# 如何设计一个可维护的后台管理系统

后台管理系统会随着角色、流程和报表不断增加。可维护性并不是某个组件库带来的，而是让每一次新增功能都能找到明确位置，并且不轻易破坏已有流程。

## 用模块边界代替“按页面堆文件”

先从业务能力划分模块，例如订单、库存、成员、审批、内容。一个模块可以拥有自己的路由、接口调用、状态和表单校验；跨模块的内容再提取为共享能力。

```text
features/
  orders/       # 订单规则与页面
  inventory/    # 库存规则与页面
  members/      # 成员与权限展示
shared/         # 通用表格、表单和请求封装
```

这样的目录不是唯一答案，但它提醒我们：页面只是业务能力的一个视图，不应该承担所有状态和规则。

## 让状态有唯一来源

一个常见问题是：列表数据、筛选条件、弹窗表单和详情页各自维护一份相近数据。更新某一处后，其他区域没有同步，就会出现难以定位的“偶发问题”。

### 可以先统一的三类状态

1. URL 状态：分页、筛选、排序，便于分享和刷新后恢复。
2. 服务端状态：列表、详情和权限，明确缓存与失效时机。
3. 局部交互状态：弹窗开关、输入草稿和短暂提示，不外溢到整个应用。

## 把异常流程写进界面

管理端不只要有成功流程。权限不足、网络失败、数据为空、保存冲突和异步处理中都需要可见反馈。与其在页面里散落 `catch` 分支，不如定义可复用的请求状态和错误文案。

| 场景     | 页面应该做什么                       |
| -------- | ------------------------------------ |
| 无权限   | 说明原因，并回到仍可访问的范围       |
| 空数据   | 解释下一步操作，不填充假的业务记录   |
| 保存失败 | 保留用户输入，并给出可理解的重试方式 |
| 数据更新 | 刷新必要区域，不让整个页面闪烁重载   |

## 小结

当业务模块、状态来源和异常反馈都清晰后，后台系统才适合继续叠加权限颗粒度、复杂报表和自动化流程。可维护的系统不是一次设计完成，而是在每次变化时仍然能做出清楚的判断。
